# Cross-Robot Movement Imitation: Franka to xArm

## 1. Project Overview

This project enables a UFACTORY xArm 7-DOF robot to accurately imitate the motion of a Franka Emika Panda robot. The workflow is decoupled into two main phases:

1.  **Recording Phase:** A trajectory is planned and recorded for the Franka Panda's Tool Center Point (TCP) in a Gazebo simulation. The sequence of TCP poses (position and orientation) is saved to a file.
2.  **Playback Phase:** In a separate Gazebo simulation, the recorded poses are loaded and used as targets for the xArm's TCP. An Inverse Kinematics (IK) solver calculates the necessary joint trajectory for the xArm to follow, effectively mimicking the Franka's original motion.

This "record and playback" approach simplifies the process by avoiding the need for real-time communication between two concurrent simulations.

## 2. Key Files

### Recording (Franka)
*   **Launch File:** `franka_gazebo/launch/panda.launch`
*   **Recording Script:** `Cross_Movement/Franka_Recording/src/record_franka_poses.py`
*   **Trajectory Output:** `franka_poses.json`

### Playback (xArm)
*   **Launch File:** `xarm_gazebo/launch/xarm7_new.launch`
*   **Playback Script:** `Cross_Movement/xarm_Following/src/playback_xarm_from_poses.py`
*   **URDF for IK:** `xarm7_ik_clean.urdf` (A simplified version for the `ikpy` library)

## 3. Key Challenges and Solutions

Achieving accurate motion imitation required overcoming a critical kinematic inconsistency.

*   **Initial Problem: The "Floating" Trajectory**
    When first implemented, the xArm followed the general path of the Franka but was consistently offset, appearing to float above the target objects. This indicated a fundamental mismatch in the kinematic frames being used between the recording and playback steps.

*   **Root Cause Discovery: Flange vs. TCP**
    The investigation revealed that the issue was not due to different robot base positions, but a mix-up in the end-effector frames.
    1.  **Recording:** The recording script was implicitly using the Franka's default MoveIt end-effector, which was `panda_link8` (the robot's wrist flange).
    2.  **Playback:** The playback script was correctly configured to target the xArm's `link_tcp` (the actual tool tip).

    The system was recording the trajectory of the Franka's **wrist** and then commanding the xArm's **tool tip** to follow that path. The observed height difference was precisely the physical offset between the wrist flange and the tool tip.

*   **The Correct Solution: A Consistent TCP Pipeline**
    The final solution involved making the entire pipeline consistent with respect to the Tool Center Point (TCP), which required a two-part fix in the recording script:
    1.  **Correcting the Recording Frame:** The script (`record_franka_poses.py`) was modified to explicitly set the end-effector link for MoveIt to `panda_hand_tcp`. This ensured the recorded trajectory was of the actual tool tip.
    2.  **Adjusting Target Poses:** This change meant the hardcoded waypoints in the script, originally defined for the flange, were now incorrect. The `z`-height of the critical grasp and place poses were adjusted by subtracting the known flange-to-TCP offset (`0.1034m`, found in the Franka URDF). This commanded the TCP to the correct height to interact with objects.

*   **Timing Synchronization:**
            Initially, the xArm's playback duration did not match the Franka's recorded trajectory time. This was due to the xArm's playback script using a fixed segment duration, while the Franka's trajectory had variable time steps generated by MoveIt.
            **Solution:** The `record_franka_poses.py` script was modified to save the `time_from_start` for each pose directly from MoveIt's planned trajectory. The `playback_xarm_from_poses.py` script now utilizes these exact `time_from_start` values to ensure the xArm's motion precisely matches the Franka's timing.

With these changes, the recorded TCP trajectory from the Franka could be directly and accurately replayed on the xArm's TCP.

## 4. Running the Full Pipeline

**Part 1: Record Franka Trajectory**

1.  **Terminal 1: Launch Franka Simulation**
    ```bash
    roslaunch franka_gazebo panda.launch controller:=position_joint_trajectory_controller
    ```
2.  **Terminal 2: Run the Recording Script**
    ```bash
    roslaunch franka_recording record_moveit.launch
    ```
    Wait for the script to finish its motion. It will save `franka_poses.json`. Once done, you can close the Franka simulation (Ctrl+C in Terminal 1).

**Part 2: Playback on xArm**

1.  **Terminal 1: Launch xArm Simulation**
    ```bash
    roslaunch xarm_gazebo xarm7_new.launch
    ```
2.  **Terminal 2: Run the Playback Script**
    ```bash
    roslaunch xarm_following playback_ik.launch
    ```
    The playback script now performs the following steps:
    *   **Pre-calculation of IK:** All Inverse Kinematics solutions for the entire Franka trajectory are calculated upfront before any robot movement begins.
    *   **Move to First Pose:** The xArm first moves to the initial pose of the trajectory.
    *   **Simultaneous Execution & Logging:** Once the first pose is reached, a separate thread starts recording the xArm's actual TCP trajectory, while the remaining pre-calculated trajectory is sent to the xArm for execution. This ensures accurate timing and data capture.
